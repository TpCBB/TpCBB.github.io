提示词站安全与图片托管调整记录

发表于 2026-11-11 | 分类于 tech
把图片从 R2 迁到 Workers Static Assets，再收紧数据库匿名读取和接口限流，记录一次费用与安全调整

最近在整理自己的 AI 提示词站。项目用 Next.js 做页面和接口，数据放在 Supabase，图片原来存在 R2。这次主要看访问量增长后的费用和公开读取入口，把图片改成静态托管，也重新查了仓库和数据库的权限。

当时我比较担心的是：仓库还是公开的，项目又连着 Cloudflare 和数据库，会不会把后台也暴露出去了？我把仓库改成私有，也检查了实际提交的文件和本地 Git 历史。

继续查下去，发现了一个更具体的问题：页面已经会调用自己的 API，但数据库仍允许匿名读取。这样即使给网站接口加上限流，别人也可能从另一条路径直接查库。

先分清楚公开了什么

连接了 Cloudflare，不代表别人看到配置就能操作账号。图片域名、账号标识和有操作权限的 API 令牌，需要分开看。

真正要查的是密钥有没有进 Git、有没有被打进浏览器代码、有没有跟着本地部署文件一起上传。

这次对本地 Git 历史的扫描，没有找到当前配置的敏感密钥。不过这个结论也有范围：检查了当前凭据，不等于能保证所有历史凭据都从未泄露。仓库改成私有，也不会自动收回别人已经复制的内容。如果发现真实密钥泄露，还是要撤销或轮换，光删文件不够。

Supabase 的 key 也得分清用途。publishable key 和旧的 anon key 可以用于公开客户端，它们本身不应该被当成管理员密码。客户端到底能读什么、改什么，还要看数据库授权和 RLS。service_role 或 secret key 则是另一回事，不能交给浏览器。

查完这些，我把重点放回了数据库权限和调用路径上。

图片从 R2 迁到了 Workers Static Assets

图片这边，我最在意的是访问量上来以后，读取请求会不会继续增加费用。

这里得先把 R2 的计费说准确：它本来就免出网流量费。可能产生费用的是存储，以及超过免费额度的操作。读取对象属于 Class B 操作，所以“图片被访问得多，可能增加读取操作费用”比较准确，不能直接说成“R2 按下载流量收费”。浏览器发了请求，也不一定都对应一次落到 R2 的读取，缓存和免费额度都会影响最后的账单。

我的图库主要是一批固定图片，更新频率不高，适合跟着部署一起发布。这次实际用的是 Cloudflare Workers Static Assets：把图片作为静态资源上传，由平台直接返回文件。

线上版本也核对过了，静态资源直出已启用，Worker 优先执行关闭，没有 R2 绑定。这条图片路径不会再回头读取旧桶。配置简化后类似这样，目录和名称是示意：

按这次核对的规则，普通静态资源直出的请求免费且不限次数，静态资源存储不额外收费，也没有带宽流量附加费用。对这条图片请求路径来说，访问量增加，不会再累积 R2 的对象读取操作费用。

迁移时，我先完整备份原始文件，核对路径、大小和哈希，再保留原来的相对路径上传。数据库里的图片字段不用逐条改，网站切换图片基础地址就能继续用。新地址验证完成以后，才清空旧桶里的文件；本地备份仍然保留。图片迁走和旧账号的订阅、历史账单是几件事，不能直接画等号。

顺手把缩略图也放到发布前生成：列表使用 480 / 960 像素的 WebP，详情继续看原图。带内容哈希的缩略图设置一年不可变缓存，正常图片请求直接访问独立图片域名，不经过 Next.js 的在线图片处理。

这里的免费范围也得说清楚。静态资源有文件数量、单文件大小等限制；如果请求执行了 Worker 脚本、做了在线图片处理，或者启用了会改变计费方式的其他功能，就要重新看对应的额度和费用。

尤其是 Cloudflare 的 Workers Caching：它的 cache.enabled 开关和 _headers 里的普通 Cache-Control 响应头需要分开看。按当前规则，启用 Workers Caching 后，静态资源请求也会按 Workers 请求规则计费。我这次没有启用这个开关。

所以这次解决的是：把固定图库改为纯静态资源直出，让这部分图片访问不再因为 R2 读取次数增长而新增操作费用。 网站接口、数据库和限流存储，仍然有各自的额度和计费规则。如果以后要支持用户随时上传图片，也得重新安排上传、存储和发布流程。

上面的计费范围核对于 2026-11-11，后续调整架构时还要再核对。

页面有 API，数据库也要收权限

我的页面本来就在请求自己的列表、搜索和详情接口。这次的问题是，Supabase 还保留着匿名直读的授权。

只要这条路还开着，请求就可以跳过网站入口。页面上的按钮、搜索防抖，以及放在网站中间件里的限流，都管不到直接发给数据库 Data API 的请求。

所以这次把数据访问收口到了服务端：浏览器请求网站接口，服务端再读取数据库。数据库管理密钥只留在服务端环境里。

server-only 能在模块被误引入客户端组件时让构建报错。密钥变量也不能加 NEXT_PUBLIC_ 前缀，不然就可能进入浏览器代码。

这里还有一个容易走偏的地方：service_role 可以绕过 RLS，接口本身就更需要限制好输入和返回内容。我保留固定的查询入口和返回结构，新增、修改、删除另外校验管理令牌。管理令牌只交给受信任的服务端或本地工具；没有配置时，写入功能直接禁用。

这个站提供的是公开提示词内容。如果换成用户私有数据，服务端还得检查登录身份和数据归属，不能只把查询挪到高权限密钥后面。

视图和函数也一起检查了。用于图库的视图设置了 security_invoker = true，按调用方权限访问底层表；视图和统计函数的访问授权也只留给服务端角色，避免通过新入口重新开放数据。

限流要能跨实例计数

读取收回服务端后，入口就比较好管理了。但 Vercel 上还要考虑多实例。

进程里的 Map 可以做本地计数。线上实例一多，同一个访客的请求可能落在不同实例上，每个实例都觉得自己没超限。实例重启后，计数也会丢。

这次接了 Upstash Redis，通过 Vercel Marketplace 配置。选的是免费方案，创建时明确关闭了自动升级参数。

计数按普通读取、搜索、短时间突发分别设置，还加了站点总量预算。多个额度要一起检查，所以放进同一个 Lua 脚本：先确认所有额度都允许，再统一增长计数。被拒绝的请求不会继续增加计数，也不会反复延长等待时间。

网站首页也会查库，所以只保护 /api/* 不够。首页、HEAD 请求和带预取标记的请求都要经过检查，不能因为请求带了一个客户端能随便填写的头就跳过。

IP 也只用来做限流分组。我取部署平台提供的转发信息，再做规范化和哈希后计数。它不是登录身份，共用网络出口的用户也可能共用额度。

超过额度返回 429 和 Retry-After。这些拒绝响应加了 no-store，避免被缓存后继续影响正常请求。前端收到 429 或 503 时不自动重试，留给用户手动操作，免得页面自己把拥堵放大。

Redis 故障时，我这次选择返回 503，不继续放开查库。这个取舍会影响可用性：存储故障时，正常用户也可能暂时打不开页面。对这个小站，我先保住数据库入口，再通过错误提示和重试处理恢复。

另外，缓存和查询并发保护仍然是单实例范围。我做了短时缓存、相同请求的并发合并、数据库读取超时和并发上限，用来减少重复工作。跨实例共享的是 Redis 里的限流额度，不能把这两种范围混在一起。

上线顺序得安排好

这里最容易出问题的是先收权限，而线上旧版还在用匿名凭据读取。SQL 执行成功了，网站却跟着出错。

这次按下面的顺序做：

  1. 配好生产环境的服务端密钥和共享限流存储。
  2. 创建使用生产配置的候选部署，先不切正式域名。
  3. 验证首页、列表、搜索、分类、标签和详情，再切换正式域名。
  4. 确认正式站点运行新版后，执行数据库权限迁移。
  5. 分别验证网站读取成功、数据库直读被拒绝。

我自己的个人私有仓库继续部署没有问题，但提交身份和项目权限得对应上，不能只看本机已经登录了 CLI。

验证时，我刻意避开了缓存

改完后只刷新一次页面，还不能确定权限调整没有问题。页面可能拿到旧缓存；有些错误页面本身也能返回 200。

我除了看状态码，还检查首页有没有真实的提示词卡片、接口有没有返回预期的数据。然后用新的随机搜索条件强制走一次未缓存的查询，确认服务端确实还能访问数据库。读取失败也要和正常空结果分开处理，不能把数据库报错吞成一个成功的空数组。

数据库直读则用有效的 publishable key 去测。这样能排除“只是 key 填错了，所以访问失败”的情况。实际返回的是 401，响应里的 PostgreSQL 错误码是 42501，表示权限不足。

限流也跑了真实请求。测试时还得确认请求落在同一个时间窗口和计数分组里，不能只看脚本写了多少并发。我把请求改为复用同一连接，核对 Redis 里的共享计数，确认出现了带 Retry-After、禁止缓存的 429 响应。

最后的结果是：

  • 原始表和图库视图的匿名直读被拒绝，普通用户角色也没有直读授权。
  • 网站首页、列表、分类、标签，以及未命中缓存的查询正常返回。
  • 未授权写入返回 403。
  • 原始提示词仍是 1,110 条，默认图片列表仍展示 1,013 条，权限调整没有删除数据。两个数量的统计口径不同，默认列表还有类型、去重和内容过滤规则。
  • 整个项目的 151 项测试通过，GitHub 自动检查和生产构建也通过。其中包含权限撤销、限流、缓存并发等用例，并不都是这次新增的测试。

图片静态化处理了这批图库的读取费用问题，数据库权限和应用层限流则管网站的数据入口。它们不能保证挡住大规模分布式攻击，也不能消除所有托管平台请求费用；图片服务的访问保护还得单独管理。

以后再给这类小项目上线，我会多检查一条路径：页面平时从哪里读数据，绕过页面以后又能从哪里读到。把这两条路都走一遍，比只看页面能不能打开更有用。
